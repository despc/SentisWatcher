# Настройка продового Battle REST через PowerShell

Скрипт: [`tools/setup-battle-api.ps1`](../tools/setup-battle-api.ps1). Это **отдельный самостоятельный файл**, его можно скопировать на прод без остальных tools. Запускать через **Windows PowerShell 5.1 (`powershell.exe`)**, не `pwsh`/PowerShell 7.

## Что он делает

- Создаёт случайный 256-битный ключ в локальном приватном файле. Секрет не печатается и не передаётся аргументом внешнего процесса.
- Задаёт ACL: создатель/SYSTEM/администраторы — полный доступ, аккаунт Torch — чтение. При повторном запуске использует существующий ключ; намеренная ротация — только `-RotateKey`, в новый файл с сохранением предыдущего.
- Делает резервную копию XML и включает `PublicBattlesEnabled`, путь к ключу и задержку публикации. Сохраняет остальные настройки, комментарии, существующий `PublicPort` и `PublicOrigin`.
- При необходимости регистрирует **только loopback** URL ACL для аккаунта Torch. Существующую резервацию не удаляет.
- Опционально готовит локальному Windows-бэкенду отдельные приватные `watcher-battles.key` и `watcher-battles.env`. Основной `.env`/код приложения не трогает.
- Опционально разворачивает HTTPS-прокси Caddy как задачу Windows при старте, под **LocalService**, с автоматическим сертификатом, IP-фильтром бэкенда и ограничением маршрутов `/battles`. Административный API Caddy отключён. Ключ Watcher в конфиг Caddy не записывается.
- Сетевые правила добавляются **только с `-ConfigureHttps`**: TCP 80 для ACME HTTP challenge, TCP 443 только от перечисленных IP бэкенда. Порты Watcher 18950/18953 наружу не открывает. Чужие правила/IIS/прокси не удаляет.
- `-CheckOnly` проверяет реальный локальный REST: 401 без ключа, 200 с ключом, отсутствие CORS, доступность прежних `/online` и `/perf`.

**Это настройщик, не установщик релиза плагина и не универсальный установщик сайта.** Сначала установить версию Watcher с Battle REST. Для удалённого бэкенда нужны безопасная доставка секрета и подключение переменных именно в его приложении; скрипт не угадывает SSH-пароли, ОС и фреймворк сайта. DNS, NAT и облачные security groups также настраиваются у соответствующих провайдеров.

## Перед запуском

1. Установить новый релиз SentisWatcher в нужный экземпляр Torch.
2. Сохранить мир и **остановить именно этот Torch**. Watcher сохраняет свой конфиг при Dispose: нельзя сначала редактировать файл, а затем закрывать старый процесс — он может затереть правки.
3. Узнать аккаунт запуска Torch. Для службы — вкладка «Вход в систему», для ручного запуска — пользователь, запускающий сервер. Не подставлять аккаунт администратора настройки, если Torch запускается от другого пользователя.
4. Заменить примеры путей, аккаунтов, домена и IP на настоящие. `C:\TorchProd` и `203.0.113.10` ниже — **примеры**, не наши реальные продовые реквизиты.
5. Для URL ACL, HTTPS или управления службой открыть PowerShell **от администратора**.

`-TorchStopped` — явное подтверждение, что нужный сервер остановлен. Скрипт дополнительно проверяет видимый процесс по точному пути `TorchRoot\Torch.Server.exe`; другие экземпляры не останавливает. Если Torch запущен от другого аккаунта, выполнять проверку из повышенного PowerShell.

## Вариант A: бэкенд на той же машине

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\setup-battle-api.ps1 `
  -TorchRoot 'C:\TorchProd' `
  -TorchAccount 'SERVER\torch' `
  -TorchStopped `
  -ReserveLoopbackUrl `
  -BackendSecretsDirectory 'C:\SiteSecrets\Watcher' `
  -BackendAccount 'IIS APPPOOL\Website'
```

Для не-IIS-бэкенда `BackendAccount` — его реальный Windows-аккаунт, не обязательно IIS AppPool.

Результат:

- API: `http://127.0.0.1:18953` (либо уже настроенный PublicPort).
- Основной ключ: `Instance\SentisWatcher-Secrets\battles.key`.
- Приватная копия для бэкенда: `C:\SiteSecrets\Watcher\watcher-battles.key`.
- Отдельный фрагмент окружения: `C:\SiteSecrets\Watcher\watcher-battles.env`.

Загрузить фрагмент в конфигурацию бэкенда и перезапустить приложение. Фрагмент содержит **URL и путь к секретному файлу**, не значение ключа. Приложение должно читать файл и формировать Bearer-заголовок в памяти. Ключ не передавать браузеру.

## Вариант B: бэкенд на другой машине, новый HTTPS-прокси

Предварительно:

- Создать DNS-запись, например `watcher-api.example.org`, на внешний адрес Torch. В этом варианте — прямой DNS, без чужого CDN/proxy перед Caddy.
- TCP 80 и 443 должны доходить до Windows-хоста (NAT/маршрутизатор/security group). Порт 80 используется для выпуска/обновления сертификата; закрывать его после выпуска нельзя без альтернативной проверки домена.
- Узнать **исходящий IP бэкенда**, с которого он обращается к Torch, не IP посетителей сайта. При необходимости передать массив IPv4/IPv6.
- Взять `caddy.exe` из доверенного источника, например [официальных релизов Caddy](https://github.com/caddyserver/caddy/releases), и проверить опубликованную контрольную сумму архива. Скрипт ничего не скачивает. Опциональный `-CaddySha256` проверяет SHA256 **самого EXE**, не ZIP (официальные суммы архивов могут использовать SHA512).
- TCP 80/443 не должны быть заняты IIS/другим приложением. Скрипт не будет их вытеснять.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\setup-battle-api.ps1 `
  -TorchRoot 'C:\TorchProd' `
  -TorchAccount 'SERVER\torch' `
  -TorchStopped `
  -ReserveLoopbackUrl `
  -ConfigureHttps `
  -PublicHostName 'watcher-api.example.org' `
  -BackendIp '203.0.113.10' `
  -CaddyExe 'C:\Tools\caddy.exe' `
  -DnsReady
```

`-DnsReady` — подтверждение уже выполненной настройки DNS/NAT, не команда автоматической настройки регистратора.

Скрипт создаст:

- `Instance\SentisWatcher-BattleProxy\Caddyfile` — ограниченный reverse proxy, без секрета.
- `Instance\SentisWatcher-BattleProxy\bin\caddy.exe` — копия доверенного бинарника.
- `Instance\SentisWatcher-BattleProxy\data` — приватное хранилище сертификатов и журнал `caddy.log` (ротация по 10 MiB, до 3 архивов).
- Задачу `SentisWatcher-BattleProxy` от LocalService, запуск при загрузке Windows.
- Два правила Windows Firewall, привязанных к этому бинарнику: ACME/80 и HTTPS/443 со списком разрешённых IP.

Успешный запуск задачи **ещё не доказывает** выпуск сертификата или внешнюю доступность. Это проверяется с разрешённой машины бэкенда. Ошибки DNS, ACME и TLS — в приватном `data\caddy.log` и Планировщике задач. В конфиге нет request access log и `log_credentials`, Bearer не выводится.

На удалённом бэкенде:

1. Безопасно импортировать ключ Watcher в secret storage/приватный файл (не через чат/Git/публичную папку).
2. Указать `WATCHER_API_URL=https://watcher-api.example.org` и путь к файлу в `WATCHER_API_KEY_FILE`.
3. Подключить серверные запросы к `/battles` и `/battles/{id}`; кэшировать примерно минуту. API не вызывается напрямую из браузера.

Для Linux/Docker путь к секрету будет Linux-путём, например `/run/secrets/watcher-battles.key`, а не путём `C:\...` с Torch.

## Вариант C: HTTPS-прокси уже есть

Не запускать второй Caddy поверх существующего IIS/Nginx. Настроить маршрут в существующем прокси по [контракту REST](public-battles-api.md), а скрипту передать уже существующий внешний origin:

```powershell
.\setup-battle-api.ps1 -TorchRoot 'C:\TorchProd' -TorchAccount 'SERVER\torch' `
  -TorchStopped -ReserveLoopbackUrl -PublicApiUrl 'https://watcher-api.example.org'
```

Этот вариант не изменяет прокси и не создаёт правила 80/443.

## Запуск и проверка

После настройки запустить нужный Torch обычным способом, затем:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\setup-battle-api.ps1 `
  -TorchRoot 'C:\TorchProd' -TorchAccount 'SERVER\torch' -CheckOnly
```

Эта проверка читает ключ в память и выводит только статусы/количество опубликованных боёв, не секрет.

Вариант для **уже существующей Windows-службы Torch**: вместо `-TorchStopped` указать `-RestartTorchService 'ExactServiceName' -WorldSaved`. Сначала действительно сохранить мир. Скрипт проверит, что EXE службы находится внутри заданного TorchRoot, остановит службу **до правки конфига**, перечитает сохранённый XML и после настройки запустит её с ожиданием REST. Он не управляет произвольным Task Scheduler/ручным запуском Torch; для обёртки службы вне TorchRoot использовать ручную остановку/запуск.

Проверять внешний HTTPS нужно **с разрешённого IP бэкенда**, а не из произвольного браузера. Проверка без Bearer должна вернуть 401; правильный ключ — 200. Из других IP ожидается отказ firewall/403. Сам секрет не писать в аргументы `curl -H`, историю терминала или логи запросов.

## Дополнительные параметры и безопасность

- `-InstancePath 'D:\Instances\Main'` — если конфиг не в `TorchRoot\Instance`.
- `-PublicPort 18953` — явный выбор порта; без параметра сохраняется существующий, если 0/отсутствует — 18953. Совпадение с приватным `WebPort` запрещено.
- `-DelayMinutes 15` — задержка, допустимо 5–1440.
- `-KeyFile 'C:\TorchSecrets\battles.key'` — абсолютный локальный путь; UNC и очевидные web/public-каталоги запрещены.
- `-RotateKey` — намеренная ротация в новый файл. Остановить Torch/согласовать обновление ключа бэкенда, затем запустить; старый ключ перестанет работать после рестарта. Одновременная поддержка двух ключей не предусмотрена.
- `-WhatIf` — предварительная проверка/план без изменения файлов, задач, URL ACL, firewall и без запуска Caddy. Например, добавить к выбранной команде после остановки Torch.

Бэкапы конфига/предыдущего Caddyfile: `Instance\SentisWatcher-SetupBackups\<дата-id>`. Старый ключ при ротации не удаляется автоматически. При ошибке скрипт не обещает транзакционный откат всех компонентов Windows: нужно посмотреть сообщение и бэкап. Если он сам остановил указанную службу, при ошибке пытается запустить её снова. Чужие процессы не убивает.

Не запускать скрипт в режиме отладки с выводом значений переменных/дампом памяти. Файл ключа и каталог данных Caddy не публиковать и не отправлять целиком вместе с логами.

## Проверено при разработке

`SentisWatcher.Tests/setup-battle-api.test.ps1` — 8 групп проверок в одноразовом каталоге: WhatIf, обязательное подтверждение остановки, запрет совпадения портов, приватный ACL и бэкап, сохранение посторонних настроек/комментариев, копия секрета и env без значения ключа, идемпотентность/ротация, отказ при конфликтующем секрете, настоящая HTTP-проверка на изолированном mock-сервере, whitelist/IP/Host в Caddyfile.

Сгенерированный HTTPS-конфиг дополнительно принят реальным Caddy 2.11.9 через `validate`; официальный ZIP проверен по опубликованной SHA512. Реальная локальная `-CheckOnly` проверка на стенде также прошла. **Задача от LocalService, firewall и выпуск сертификата на продовом домене здесь не запускались:** для этого нужны администратор и настоящие сетевые реквизиты. Продовые файлы не менялись.
