# REST API сражений для сайта

Сражения выдаются через **существующий порт публичной статистики** (`PublicPort`, на стенде 18953), но отдельными защищёнными методами. `/online` и `/perf` не меняются. Приватный интерфейс Watcher на 18950 и его `/api/*` не нужно и нельзя проксировать в интернет.

## Схема доступа

```text
Браузер → бэкенд сайта → HTTPS reverse proxy на машине Torch → 127.0.0.1:18953/battles
                             Authorization: Bearer <секрет>
```

- Ключ хранится **только у Torch и бэкенда сайта**, не в JS-бандле, HTML, localStorage или URL браузера.
- Сам плагин принимает эти методы только от loopback. Внешний адрес — только через локальный HTTPS reverse proxy. `X-Forwarded-For` не используется как доказательство доверия.
- На маршрутах сражений нет CORS и cookie-аутентификации. `PublicOrigin` относится только к прежним `/online` и `/perf`; CORS не является защитой API от сторонних клиентов.
- Новые методы по умолчанию выключены. Неверный/отсутствующий файл ключа означает отказ в выдаче, не открытый доступ.
- Ключ проверяется по SHA-256 с константным по длине сравнением хешей. Он не выводится в логи или ответы.
- Только `GET`. Нельзя изменять игру, запускать замеры, читать позиции, инвентари, карты, сырые события или произвольные SQL-запросы.

## Включение

Для автоматической настройки на Windows есть самостоятельный [`tools/setup-battle-api.ps1`](../tools/setup-battle-api.ps1):
ключ/ACL, бэкап XML, настройки API, опциональные файлы секретов бэкенда и HTTPS-прокси Caddy.
**[Пошаговые команды для прода](setup-battle-api.md)**. Ниже — ручной вариант.

1. Создать отдельный случайный ключ с приватным ACL (Windows PowerShell 5.1):

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\create-battle-api-key.ps1 `
     -Path C:\SE\Instance\SentisWatcher-Secrets\battles.key `
     -ServiceAccount 'DOMAIN\TorchAccount'
   ```

   Если Torch работает от текущего пользователя, `-ServiceAccount` не нужен. Скрипт создаёт **новый** файл, отказывается перезаписывать существующий и не печатает ключ. Приватный ACL устанавливается при создании: создатель/администраторы/SYSTEM и указанный аккаунт Torch. Не помещать файл в каталог сайта, `Web` или другой публичный каталог. Используется 32 случайных байта в Base64 (256 бит).

2. В `Instance\SentisWatcher.cfg`:

   ```xml
   <PublicPort>18953</PublicPort>
   <PublicBattlesEnabled>true</PublicBattlesEnabled>
   <PublicBattlesKeyFile>C:\SE\Instance\SentisWatcher-Secrets\battles.key</PublicBattlesKeyFile>
   <PublicBattlesDelayMinutes>15</PublicBattlesDelayMinutes>
   ```

   Это путь, **не значение ключа**. Перезапустить Torch. Пустой/недоступный файл, сетевой путь, файл больше 512 байт, ключ короче 32/длиннее 256 ASCII-символов или с пробелами внутри — выдача закрыта. Допускается завершающий перевод строки. Ключ читается один раз при старте.

3. Безопасно передать этот же ключ в секрет-хранилище бэкенда сайта. Не передавать его в чат, коммиты, query string или команды с открытым аргументом `-H 'Bearer ...'`, попадающим в историю/список процессов. Для локальной проверки Python может прочитать файл и сформировать заголовок в памяти:

   ```python
   from pathlib import Path
   import json, urllib.request

   key = Path(r'C:\SE\Instance\SentisWatcher-Secrets\battles.key').read_text(encoding='utf-8-sig').strip()
   request = urllib.request.Request(
       'http://127.0.0.1:18953/battles?hours=24&page=1&pageSize=20',
       headers={'Authorization': 'Bearer ' + key})
   with urllib.request.urlopen(request, timeout=30) as response:
       data = json.load(response)
   print(data['total'])  # Не печатать key/request.headers.
   ```

4. Для доступа с другой машины настроить HTTPS reverse proxy, сертификат и ограничение по IP бэкенда сайта. Не открывать приватный 18950. Не передавать bearer через незашифрованный внешний HTTP.

### Пример Nginx

Не готовый серверный конфиг: фрагмент для **уже настроенного TLS virtual host**, например `watcher-api.example.org`. Сначала заменить разрешённый IP на реальный адрес бэкенда сайта.

```nginx
# Внутри http {}, один раз:
limit_req_zone $binary_remote_addr zone=watcher_battles:10m rate=1r/s;

# Внутри server {} с listen 443 ssl и своим сертификатом:
location ~ ^/battles(?:/[a-f0-9]{32})?$ {
    # Дополнительная защита: разрешить только реальный IP бэкенда сайта.
    # allow <SITE_BACKEND_IP>;
    # deny all;
    limit_except GET { deny all; }
    limit_req zone=watcher_battles burst=5 nodelay;
    limit_req_status 429;
    proxy_pass http://127.0.0.1:18953;
    proxy_set_header Host 127.0.0.1;
    proxy_set_header Authorization $http_authorization;
    proxy_read_timeout 30s;
    proxy_hide_header Access-Control-Allow-Origin;
    add_header Cache-Control "private, no-store" always;
}
```

Не добавлять заголовок Authorization в access logs. На HTTP-порту делать перенаправление на HTTPS, но бэкенд должен изначально обращаться к HTTPS, чтобы не отправить ключ по открытому каналу. Публичный порт Torch рекомендуется закрыть от интернета брандмауэром, оставив доступ локальному proxy; это особенно важно для защиты от перегрузки до уровня приложения.

## Что публикуется

Только **завершённые** бои, ещё через 15 минут после окончания. Минимальная задержка — 5 минут, максимальная — сутки. Окончание — после 120 секунд без связанного урона, а не само последнее попадание. Живые бои и бои с неполными границами не публикуются. Свежий бой не получится прочитать напрямую по угаданному ID: подробности доступны только для опубликованного каталога и повторно проверяются перед выдачей.

Из внутреннего отчёта берётся явный белый список:

- название (`ZRG vs SVP`), времена, длительность, урон, попадания, убийства, разрушения;
- имена участников, фракции и личные итоги;
- кто → кому → чем, отношение сторон, тип атакующего/цели;
- таймлайн урона и связанный список прыжков: время, направление, дальность, имена инициатора/пассажиров;
- экономические потери сторон: повреждённые/разрушенные блоки, состав утраченных компонентов и стоимость в SC;
- безопасные ссылки между строками отчёта.

`report.economy` — совместимое добавление к REST v1: [формат и точная методика](battle-economy.md). Стороны получают отдельные локальные `l1`, `l2`; приватные ссылки на урон и runtime-токены блоков не выходят в API. До 64 сторон, до 256 типов компонентов на сторону с `truncated`. `credits/knownCredits` — десятичные строки для точности больших сумм; NULL полного итога не равен нулю ущерба. При `partial` показывать известную часть как нижнюю границу, при `unavailable` не рисовать нулевые потери. `recordingInterrupted=true` означает, что уникальные счётчики блоков между сеансами неизвестны (NULL). Задержка публикации не меняется. При полном учёте экономические потери теперь входят в сводный результат победы с весом 50%; см. раздел результата ниже.

**Не выдаются:** координаты, Steam ID, SE identity/entity/faction IDs, `factionKey`, позиции, содержимое инвентарей, детали прыжка `to=x;y;z` и сырой журнал событий. Имена/теги игроков — пользовательский текст: на сайте выводить через `textContent`/экранирование, не через `innerHTML`.

ID боя — внешний 32-символьный hex-идентификатор, а не исходное `timestamp:row`. Участники внутри отчёта обозначаются `p1`, `p2`, объекты — `e1`, `e2`; это временные локальные ссылки, не ID игры и не способ сопоставить корабль между разными боями. В `entities[].name` публикуются сохранённые названия кораблей/станций и других объектов. Если имя отсутствует или вместо него известен только игровой ID, используются подписи «Грид 1», «Персонаж 2», «Объект 3». Имена ограничены по длине, очищены от управляющих символов и длинных числовых ID; координаты и сырые детали прыжка по-прежнему не выдаются. Сайт обязан экранировать эти пользовательские имена.

## Методы

### `GET /battles?hours=24&page=1&pageSize=20`

Заголовок: `Authorization: Bearer <ключ>`.

- `hours`: 1–168, по умолчанию 24. Окно отсчитывается от `availableThrough`, то есть от текущего времени **минус задержка публикации**, не от текущего момента.
- `page`: 1–1000, по умолчанию 1.
- `pageSize`: 1–50, по умолчанию 20.
- Порядок: новые бои первыми. Каталог — максимум 1000 последних подходящих боёв в выбранном окне (до 7 суток). Запрос за 24 часа не начинает с обязательного чтения всей недели.
- `from`, `to`, произвольные фильтры, `gap`, `radius`, дублирующиеся или неизвестные параметры не принимаются. Это предотвращает разрастание ключей кэша и произвольные тяжёлые выборки.

```json
{
  "schemaVersion": 1,
  "generatedAt": 1800000000000,
  "availableThrough": 1799999100000,
  "delayMinutes": 15,
  "from": 1799912700000,
  "to": 1799999100000,
  "page": 1,
  "pageSize": 20,
  "total": 1,
  "truncated": false,
  "battles": [{
    "id": "0123456789abcdef0123456789abcdef",
    "title": "ZRG vs SVP",
    "start": 1799998800000,
    "end": 1799998860000,
    "endedAt": 1799998980000,
    "duration": 60000,
    "damage": 100000,
    "combatDamage": 90000,
    "hits": 100,
    "kills": 1,
    "destroyed": 50,
    "participants": ["Alice", "Bob"],
    "participantsTotal": 2,
    "factions": ["[ZRG] Zerg", "[SVP] Vanguard"],
    "weapons": ["Bullet:LargeRailgun"],
    "truncated": false
  }]
}
```

Все времена — UTC epoch milliseconds. `duration` — от первого до последнего связанного урона; `endedAt` включает двухминутное ожидание тишины. `damage` включает контекст, `combatDamage` — основу по врагам/нейтралам.

### `GET /battles/{id}`

Тот же заголовок. Дополнительные query-параметры не принимаются. Идентификатор нужно брать из списка, а не вычислять самому.

```json
{
  "schemaVersion": 1,
  "generatedAt": 1800000000000,
  "availableThrough": 1799999100000,
  "delayMinutes": 15,
  "report": {
    "summary": { "id": "0123456789abcdef0123456789abcdef", "title": "ZRG vs SVP" },
    "participants": [
      { "id": "p1", "name": "Alice", "faction": "[ZRG] Zerg", "dealt": 100000, "taken": 0, "kills": 1, "deaths": 0, "destroyed": 50, "lost": 0 },
      { "id": "p2", "name": "Bob", "faction": "[SVP] Vanguard", "dealt": 0, "taken": 100000, "kills": 0, "deaths": 1, "destroyed": 0, "lost": 50 }
    ],
    "entities": [{ "id": "e1", "kind": "grid", "name": "Грид 1" }],
    "breakdown": [{
      "attacker": "p1", "victim": "p2", "attackerKind": "player", "targetKind": "block",
      "source": "e1", "target": null, "weapon": "Bullet:LargeRailgun", "relation": "enemy",
      "damage": 100000, "hits": 100, "kills": 1, "destroyed": 50
    }],
    "timelineFrom": 1799998800000,
    "timelineTo": 1799998862000,
    "timeline": [{ "t": 1799998800000, "width": 2000, "damage": 10000, "combatDamage": 9000 }],
    "jumps": [{
      "t": 1799998860000, "grid": "e1", "direction": "departure", "distance": 20000,
      "actors": [{ "name": "Alice", "role": "pilot" }, { "name": "Passenger", "role": "passenger" }]
    }],
    "truncated": false
  }
}
```

Пример сокращён: `summary` содержит все поля из списка, а `timeline` — все интервалы, включая нулевые. `source`, `target`, `grid` ссылаются на `entities`; `attacker`/`victim` — на `participants`. Неизвестная ссылка может быть `null`. Расстояние прыжка — в метрах. Названия фракций старых записей остаются неизвестными.

## MVP, результат сторон и личные счётчики

Подробный отчёт дополнен `participants[].shots`, `hitShots`, `accuracy`, `accuracyStatus`, `jumpCount`,
`combatDealt`, `combatTaken`, `attributionKnown` и объектом `mvp`. В `mvp.players` — локальные ссылки `p1` и т. п.
В выбранном отчёте `summary.outcome` содержит результат `weighted_shares_v1`: +35% доля нанесённого урона, −15% доля полученного, −50% доля стоимости собственных потерь. `method/weights/economyIncluded` описывают реально применённый расчёт; `sides[].score` — балл, `lossCredits` — точная десятичная строка либо NULL. При неполной экономике — damage-only fallback 70%/30% с явным предупреждением; неизвестные потери не становятся нулевыми. В лёгком каталоге outcome=NULL, экономика читается только для выбранного отчёта. Совместимое поле balance не определяет победителя и не показывается колонкой;
стороны имеют только локальные ID `s1` и т. п., не ID фракций игры.

**[Точные правила, статусы недоступности данных, примеры полей и ограничения старых записей](battle-statistics.md).**
Не делить старый `summary.hits` (события повреждения) на shots: меткость считается по отдельным снарядам.
При неизвестной телеметрии процент NULL; при неизвестных фракциях/источниках нет подтверждённого победителя.

## Кэш и ограничения

- Один общий снимок каталога на 5 минут (`CatalogMs`), а не отдельный дорогой запрос для каждого `hours/page`. Изначально читается ближайшее покрывающее окно 24/72/168 часов; фильтр hours применяется точно. Более широкое окно расширяет снимок, меньшие окна и страницы используют существующий. Таким образом, последовательные hours=1,2,3… не вызывают отдельное чтение БД для каждого значения. [Проверка загрузки и замеры](battle-catalog-loading.md).
- Снимок строится в процессе Torch, из записей целых суток. На продовой базе (11.11.2026, 18 000 строк урона в сутки) неделя стоит 1,5–2 с процессора и 200 МБ памяти, сутки — 0,25 с и 30 МБ. Поэтому снимок живёт 5 минут: бой всё равно публикуется через 15 минут после конца.
- Если ID нет в узком снимке, окно членства расширяется до 168 часов, чтобы старые прямые ссылки продолжали работать. Расширение — не чаще раза в 5 минут; иначе такой ID сразу получает 404. Произвольные 32 hex через сайт поэтому не заставляют Torch читать неделю на каждый запрос. Неизвестный ID не запускает построение подробного отчёта.
- Отчёт опубликованного боя не меняется: он хранится, пока бой есть в каталоге (до 64 отчётов и 16 млн символов JSON), и не строится заново. Новых отчётов строится не больше 6 в минуту (`ReportsPerMinute`), сверх — `503` с `Retry-After`. Авторизация, задержка и проверка завершённости сохраняются.
- В выборке только списка не читаются ключи связи экономики/метки атрибуции и не разрешаются имена гридов. Поиск связанных событий ограничен временным окном на отсортированной активности, без повторного перебора всей истории длинного боя.
- Максимум одна операция чтения/построения из этого API одновременно; при занятости — `503` с `Retry-After`, без очереди тяжёлых задач.
- Общий лимит авторизованных запросов — 60 в минуту. Рекомендуется кэшировать данные на бэкенде сайта на минуту, а не обращаться к Torch на каждое открытие страницы браузером.
- Запросы не вызывают игровые методы; используются только read-only суточные БД.
- Список: до 50 боёв в ответе, в кратком описании до 64 имён/32 фракций. Подробности: до 512 участников, 2000 строк урона, 500 прыжков и 64 человек на прыжок. Строки ограничены по длине. При достижении количественных ограничений есть `truncated: true`; игнорировать этот флаг при подсчёте итогов нельзя.
- Чрезмерно большой подробный JSON не выдаётся (`503`). Ответы имеют `Cache-Control: private, no-store`, `Vary: Authorization` и `X-Content-Type-Options: nosniff`. Серверный кэш не отменяет проверку авторизации.

| Код | Значение |
|---|---|
| 200 | Данные |
| 400 | Неизвестные/неверные параметры, повторяющиеся ключи, длинный query |
| 401 | Нет/неверный bearer; `WWW-Authenticate: Bearer` |
| 403 | Прямой не-loopback запрос; нужен локальный TLS proxy |
| 404 | Публикация выключена, неверный/неопубликованный/слишком старый ID |
| 405 | Не GET; CORS/preflight для прямого доступа из браузера не поддерживается |
| 429 | Лимит; `Retry-After: 60` |
| 503 | Нет корректного файла ключа, идёт построение отчёта/каталога или превышен лимит ответа; следовать `Retry-After` |
| 500 | Внутренняя ошибка без раскрытия деталей |

## Ротация

Создать новый приватный файл (существующий скрипт не перезаписывает), безопасно обновить секрет бэкенда и `PublicBattlesKeyFile`, перезапустить Torch. После рестарта прежний ключ больше не действует. Для отключения — `PublicBattlesEnabled=false` и рестарт. `/online` и `/perf` при этом продолжают работать.
